# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, unpacked Manifest V3 Chrome extension with power-user features across **instagram.com, youtube.com, x.com, and reddit.com** (see `README.md` for the full user-facing list and `PRD.md` for the roadmap; LinkedIn and TikTok support existed and were removed by user request, 2026-08). Each site gets its own `content_scripts` entry in `manifest.json`, loaded only on that host; `config.js`, `queue.js`, and `ui.js` are shared across all hosts (each platform's tunables live in its own `cfg.<PLATFORM>` block). The foundational Instagram features:

1. **Shift-click instant unfollow/remove** in the Following and Followers list modals.
2. A **"doesn't follow you back" subsection** injected into your own profile's Following modal, with throttled bulk unfollow.
3. **Resizable Followers/Following modals** — drag any edge/corner of the modal card (any profile) to resize it both ways; the size is persisted (`bwi_modal_size`) and double-click on a handle resets. Height is verified at runtime and rolls back to width-only if Instagram's list can't grow — see the Feature 3 bullet below. `BIGGER_MODALS` (still default-off) is now just an initial width.
4. **Bulk unsave on the Saved page** — an inline "Select" mode over the saved-post grid; toggle individual tiles, then "Unsave (n)" fully unsaves the selection through the throttled queue.
5. **Keyboard story navigation** — while viewing a story, `H` jumps to the previous user's story and `L` jumps to the next user's story, skipping any remaining frames of the current person (toggle via `STORY_NAV` in `src/config.js`).

One later feature survives: **see-who-unfollowed** (`feature7.js`), documented in `README.md` / `PRD.md`. The **enhanced story composer** (`feature9.js`) was removed by user request (2026-08) along with its story-upload core in `ig-api.js` (`ruploadPhoto`/`configureToStory`), the `STORY` config block + `STORY_CREATE_TOOLS` toggle, its styles, and the popup's stories counter — do not rebuild unless asked.

**Removed as impossible/native on web** (see `FEATURE_FEASIBILITY_REPORT.md`, and Non-Goals in `PRD.md`) — do not re-add: **story repost** (web ships no story-create call; the finalize endpoint is mobile-tier and flags web-cookie sessions), **per-collection unsave** (collection membership is mobile-app-only; web silently full-unsaves), **carousel reorder** (Instagram web now reorders natively), **bio-link editing** and **Emoji Pong** (both mobile-app-only). The story composer's interactive link/poll stickers were cut for the same reason (web configure silently drops them).

### Important correction: "Bulk unlike"

`PRD.md` lists **"Bulk unlike"** in the *Existing Features* table as "Shipped", and commit `bf16c09` reinforces this. **This is misleading.** Bulk unlike is a **native Instagram feature** (Settings → Your activity → Interactions → Likes, where you can multi-select and remove likes). It was **not built by this extension** — there is no bulk-unlike code anywhere in this repo. When the PRD says "same pattern as Bulk Unlike," read that as **"same pattern as bulk unfollow"** (`feature2.js` + `queue.js` + `ig-api.js`), which is the reference implementation for any new bulk action.

## Commands

There is **no build step and no package manager** — it's plain vanilla JS loaded directly as content scripts. The only automated test is the Feature 3 fixture below; everything else is verified by hand on the live sites.

- **Syntax-check after edits:** `node --check src/<file>.js` (and `node -e "JSON.parse(require('fs').readFileSync('manifest.json','utf8'))"` for the manifest).
- **Modal fixture (Feature 3 resize + panel toggle):** `test/fixtures/ig-modal.html` is a network-free stand-in for Instagram's Followers/Following modal that loads the real `styles.css`, `src/config.js`, `src/ui.js`, `src/feature3.js` via `file://` (with a `chrome.storage.local` shim) and exposes `window.__fx` (drag/dblclick/reopen/rects/toggleState). Query params pick the list mode (`mode=fixed|flex|window|clip`), the panel (`title=following|followers`, `panel=0`), centering, etc. `bash test/fixtures/check.sh` runs the ~60-assertion checklist through the gstack `browse` headless browser (`~/.claude/skills/gstack/browse/dist/browse`); `test/fixtures/README.md` documents the variants, the `__fx` API and the gotchas (browse's `js` needs an explicit `return` around awaited code — `check.sh` adds it). It is not shipped: `scripts/package.sh` zips only the runtime paths.
- **Package for the Chrome Web Store:** `./scripts/package.sh` → `dist/socialfix-<version>.zip` (syntax-checks first, then zips only runtime files with `manifest.json` at the zip root). Bump `manifest.json` `version` first — the store requires a strictly increasing version per upload. `scripts/gen-icons.js` regenerates `icons/` plus the padded store-listing icon, `scripts/gen-promo.py` the promo tiles; both are dependency-free and only need re-running if the artwork changes. `PUBLISHING.md` holds the submission walkthrough and listing copy.
- **Run / verify:** load unpacked at `chrome://extensions` (Developer mode → Load unpacked → repo root), then exercise on a live, logged-in instagram.com or youtube.com tab. Behavioral verification is manual — there is no way to test against a site's real DOM/API without a logged-in browser session.
- **Safe testing:** set `DRY_RUN: true` in `src/config.js` so every mutating action (IG unfollow/remove/unsave, YT playlist removals, X unlikes/unfollows, Reddit unsaves) is logged to the console instead of performed.

## Architecture

Content scripts run in Chrome's **isolated world** and share one `window` object. Everything hangs off a single `window.BWI` namespace; each file does `const BWI = (window.BWI = window.BWI || {})` and attaches its exports (`BWI.config`, `BWI.api`, `BWI.queue`, `BWI.ui`, etc.).

**Load order is significant** and is fixed per-host in `manifest.json` `content_scripts`:

- **instagram.com:** `config → ig-api → queue → ui → feature1 → feature2 → feature3 → feature4 → feature5 → feature7`. The `feature6`, `feature8`, `feature9`, `feature10`, and `feature11` slots are intentionally vacant — bio-links (6), story repost (8), carousel reorder (10, along with the former `src/mainworld.js`), and Emoji Pong (11) were removed as impossible/native, and the enhanced story composer (9) was removed by user request (2026-08); files were **not** renumbered.
- **youtube.com:** `config → queue → ui → yt-bulk → yt-keys` (no `ig-api` — the YT modules are pure DOM automation; `queue.js` resolves `BWI.api` lazily so it loads fine without it).
- **x.com:** `config → queue → ui → x-api → x-feed → x-hide → x-keys → x-unlike → x-unfollow`. `x-api.js` exposes `BWI.xApi` (now just the batched follow-back lookup — X's one surviving v1.1 read, cookie-authed); only `x-unfollow` uses it, and the DOM-only features (`x-feed`, `x-hide`, `x-keys`, `x-unlike`) don't.
- **\*.reddit.com:** `config → queue → ui → reddit-unsave → reddit-hide`.

There is no MAIN-world content script anywhere. A file may only reference `BWI.*` symbols defined by an earlier file in its host's entry. If you add a file or a cross-file dependency, update the relevant order. Shared DOM helpers used by more than one feature (e.g. `ui.dialogTitleIs`, `ui.findScrollContainer`, `ui.insertAboveList`, `ui.toast`, `ui.buildCollapseToggle`) live in `src/ui.js`. Both injected Instagram panels (`renderSubsection` for Feature 2, `renderListSubsection` for Feature 7) get their collapse control from `ui.buildCollapseToggle`: a `▴ Hide` / `▾ Show` pill (glyph and label are separate spans, swapped in JS — down for Show, up for Hide) followed by the title, all one button. **Never rotate/transform `.bwi-caret` in CSS** — an earlier version rotated the whole span -90° when collapsed, which turned the "Show" text sideways and hid the arrow (Aug 15 fix).

The features are deliberately built on **different strategies**:

- **Feature 1 (`src/feature1.js`) uses no API at all.** A capture-phase click listener flags a Shift+click on a row's trigger button, then a `MutationObserver` auto-clicks the destructive button in Instagram's *own* confirmation UI once it appears (<100ms, looks instant). This rides Instagram's native flow, so it's the most resilient part. It never calls the private API. Hardened 2026-08 (Aug 3 audit): the confirm can arrive as a new dialog, as content **swapped into the already-open dialog** (caught via `closest()` on added nodes), or as a Cancel-less options sheet that may chain into a second confirm. The arming window is the dangerous part — a first pass kept it armed for 4s after firing, so an ordinary un-shifted click on another row got its options sheet auto-confirmed into a real unfollow. The rules that prevent that, all load-bearing: **any non-shift click disarms** (`selfClicking` guards our own synthetic clicks), the base window is 2.5s and the chained follow-up only 1.2s, the chained click accepts **only** a Cancel-bearing classic confirm (never a second Cancel-less sheet), the destructive text must match exactly one clickable, `[data-bwi]` subtrees are excluded, and a Cancel-less dialog is trusted only if it has no `input` (the list modal always has its search box).
- **Feature 2 (`src/feature2.js` + `src/ig-api.js`) uses Instagram's private web API.** `ig-api.js` calls `/api/v1/friendships/...` same-origin with `credentials: 'include'`, so the session cookies are sent automatically — there is no login/auth code. It paginates the full following + followers lists, computes the set difference, and unfollows. This is the fragile part: endpoint paths and required headers (`X-IG-App-ID`, `X-CSRFToken`, `X-IG-WWW-Claim`) are all isolated in `ig-api.js`. Detection does **not** depend on the URL changing to `/<user>/following/` (Instagram opens the list as a client-side modal and may not push that URL); it identifies the modal by ARIA role + title text and confirms ownership via the profile path segment.
- **Feature 3 (`src/feature3.js`) is pure DOM, no API — modal sizing: drag-to-resize (default on) + the legacy one-shot widen (`BIGGER_MODALS`, default off).** It finds the Followers/Following list dialog (any profile), the native scroll container (`ui.findScrollContainer`) and the visible rounded card (`findCard`), and appends a `pointer-events:none` `.bwi-resize-layer` **inside the card** (so Instagram's "click outside closes" logic still sees the pointer inside it) holding eight transparent `.bwi-resize-handle--{n,s,e,w,ne,nw,se,sw}` handles. Drags use pointer capture; a centered card grows by 2× the pointer delta so the dragged edge tracks the mouse; sizes are clamped (`MODAL_MIN_WIDTH_PX/HEIGHT_PX` … 95vw/95vh) and persisted (debounced) to `chrome.storage.local[MODAL_SIZE_KEY]` as `{w,h,hBlocked}`; double-click (or a double-press) on a handle resets. **Width is layout-safe; height goes through three runtime modes** because Instagram's list container may (a) flex with the card, (b) have a fixed pixel height, or (c) be a virtualizer that won't render into a taller box: the first ≥24px height change probes the list (`"flex"` = it followed the card, we never touch it; `"fixed"` = we set the list's inline height to fill the card below the header + injected panel, measured live), then `verify()` ~800ms later (and after every drag) checks the taller box really renders — **blank/windowing** (content box reaches the bottom but no/too-few rows mounted, or the rows' own container ends ≥150px below the last mounted row) or **clipping** (`elementFromPoint` just inside the list bottom lands on something *inside our dialog* that isn't the list; any hit *outside* the dialog — a stacked options/confirm sheet, its backdrop, a fixed banner/toast — is "unsure", re-checked a few times, never a verdict; a hidden tab is also never judged) — and a symptom that holds twice → `rollback()`; a `"flex"` verdict that doesn't hold at verify time is re-run once as `"fixed"`, and a card that refuses to change height across 5 probes rolls back as `"card-locked"`: `listMode="none"` for the page session, all our heights removed (Instagram's original inline height restored), `bwi-resize--width-only` hides the vertical handles, the stored `h` is kept but marked `hBlocked` (not re-applied next load; a new vertical drag retries), one toast. In `"fixed"` mode the card is floored at header + panel + 120px list so the list can never hang below the card (a shorter card is not "clipping"). The injected panels get a share of extra height via `--bwi-list-max` (`.bwi-list` max-height; 240px + 40% of height beyond the natural layout). **Every inline write is idempotent** (`own`/`disown` compare value+priority) because the MutationObserver watches `style`/`class` attributes (React strips inline styles) — our own writes fire it too, and idempotency is what keeps it quiescent; the synthetic `resize` dispatch is rAF-coalesced with a loop breaker. The east strip is shortened to the header zone when the native list shows a classic scrollbar (`offsetWidth − clientWidth ≥ 4`), so grabbing the scrollbar never resizes. History: the Aug 1 build forced card + list heights unconditionally and was reverted after the native list rendered blank (a likely contributing cause was the panel being inserted as a flex-row sibling of the list — since fixed by `ui.insertAboveList` — but that was never proven, which is why the detection/verification above is what makes height safe to try again). Test surface: `BWI.modalResize = { stateFor(dialog), reset(), applyAll() }` plus the checked-in fixture `test/fixtures/ig-modal.html` (see the Commands section). The injected panels (Features 2 and 7) remain hardened CSS-wise (bounded max-height, `box-sizing`, `min-width:0`) and `ui.insertAboveList` inserts them so they stack **above** the native list even when Instagram's wrapper is a flex row.
- **Feature 4 (`src/feature4.js` + `src/ig-api.js`) uses the private API + the shared queue.** On your own Saved page it injects a toolbar above the post grid with a "Select" toggle. In select mode a capture-phase click listener intercepts tile clicks (blocking navigation) and tracks the selection **by post shortcode** (not DOM node — the grid is virtualized and recycles nodes on scroll, so overlays are re-applied on mutation). The numeric media id needed by the unsave endpoint is derived locally from the shortcode via `api.shortcodeToMediaId()` (base64 decode — no extra network read), and the unsave calls run through `queue.js`. **Endpoint (2026):** Instagram removed the old REST `/api/v1/media/{id}/unsave/` (404) — `api.unsave` now POSTs to `/api/v1/web/save/{id}/unsave/`, the surviving web endpoint (verified with a live net-zero unsave→save round-trip). The Saved page is now split: `/<you>/saved/` is a collections **index** (folders, no post grid) while the grid lives at `/<you>/saved/all-posts/` or inside a collection — the feature works in the latter two and shows a one-time hint on the bare index pointing at "All posts".
- **Feature 5 (`src/feature5.js`) is pure DOM, no API — closest in spirit to Feature 1.** A capture-phase `keydown` listener (active only when `location.pathname` starts with `STORY_NAV_PATH_PREFIX`, i.e. `/stories/`) maps `H`/`L` (from `STORY_NAV_KEYS`) to previous/next *user* and clicks Instagram's own on-screen control rather than reconstructing tray order. Per repo convention the control is resolved by stable URL shape first — the dimmed neighbor-story anchors `a[href^="/stories/"]` flanking the active story, picking the visible one nearest viewport center on the requested side — and falls back to the round chevron buttons by aria-label (`LABELS.storyPrev`/`storyNext`). It no-ops on modifier keys and when focus is in an input/textarea/contenteditable (so `H`/`L` in the story reply box are untouched), and toasts "No previous/next story" when no control is found. The keys deliberately differ from the arrow keys, which step one frame at a time. **`H`/`L` (not the PRD's originally-proposed `J`/`K`) are intentional** — horizontal left/right mirrors the spatial direction of story navigation.
- **Feature 7 (`src/feature7.js`) — see-who-unfollowed.** Read-only: on your own Followers modal it snapshots your follower set to `chrome.storage.local` and diffs against the prior snapshot to surface who left. Reuses `ig-api.js`'s follower pagination; correctly bypasses `queue.js` (read-only, not a mutation). An implausibly large drop is distrusted **once** and re-checked: the count is stored as `suspectCount` and the snapshot's `ts` is stamped anyway (so the 6h throttle still applies), then a later scan landing within ~10% of it is accepted as real. Before that second chance existed, a genuine follower purge left the panel permanently stuck on stale results *and* re-paginated the whole list on every modal open.
- **YouTube bulk-remove (`src/yt-bulk.js`) — pure DOM automation, Feature-1 spirit.** On `/playlist?list=WL|LL` it injects a Select toolbar; each queued removal opens the row's own ⋮ menu (aria-label) and clicks the native "Remove from …" item (visible text from `cfg.YT.LABELS`), riding YouTube's real flow — no InnerTube/SAPISIDHASH. **It drives two row renderers:** Watch Later still uses the classic `ytd-playlist-video-renderer` ("Action menu" ⋮ + `ytd-menu-service-item-renderer` items), while YouTube migrated Liked videos to `yt-lockup-view-model` rows (a "More actions" ⋮ whose menu items are `yt-list-item-view-model`) — both are detected and handled. Selection is tracked by **videoId** (parsed from each row's `/watch?v=` link), not DOM node. Runs through `queue.js` with a **function action** and deliberately slow 5–8 s delays (YouTube processes deletions async; faster makes items reappear). Separate daily keys per playlist (`bwi_daily_wl_remove_` / `bwi_daily_unlike_yt_`). The function action must honor `cfg.DRY_RUN` itself (there's no API layer to do it). **Menu items are matched only inside a VISIBLE dropdown** (`isVisible()`): YouTube keeps the previous row's menu in its global popup container after close (`display:none`) with identical text still bound to the *previous* video, so a document-wide text match clicked the stale item — removing nothing while reporting success. Removal is confirmed by the row detaching, and a row that survives the wait **throws** rather than counting as done. Handles SPA navigation via `yt-navigate-finish` + MutationObserver — and **every row query is scoped to the visible `ytd-browse:not([hidden])`** (Aug 3 audit): YouTube's SPA keeps the page you left alive as a hidden cached page whose `yt-lockup-view-model` tiles also match `ROW_SEL`, so an unscoped query right after clicking into Liked/Watch Later injected the toolbar into the hidden old page (invisible until refresh); `maybeInject` also self-heals a toolbar stranded outside the visible browse.
- **YouTube shortcuts (`src/yt-keys.js`) — Feature-5 spirit.** What the feature *is*: YouTube ships a large native keyboard-shortcut set (k/j/l play-pause-seek, f fullscreen, m mute, c captions, arrows, 0–9 seek-to-percent, Shift+N/P next/prev video, etc.) but has **no shortcut for four common actions** — this adds exactly those four gap-fills on watch pages and nothing that overlaps a native key: `E` toggles Like, `Shift+E` opens Save-to-playlist, `Shift+U` subscribes, `N` jumps to and focuses the comment box (`cfg.YT.KEYS`; never fires while typing in a text field). Do not rebuild K/J/L/F/M/etc. Mechanism: capture-phase `keydown` clicking native buttons by aria-label/visible text; `N` clicks the comment box's `#placeholder-area` **container** (clicking the inner text node doesn't open the editor). No queue (single non-destructive actions). Selectors use semantic custom-element tags (`ytd-watch-metadata`, `ytd-menu-service-item-renderer`) — stable for years, unlike class names — plus aria-labels and text.
- **X private API (`src/x-api.js` → `BWI.xApi`) — slimmed to one read.** X removed the v1.1 friends-list endpoints in 2026 (`friends/list.json` and `friends/ids.json` now 404), so `fetchAllFollowing`/`destroyFollow` were removed; all that remains is the batched follow-back check via `friendships/lookup.json`. Same-origin to `x.com/i/api/1.1/…` with `credentials:'include'`; authed by the static **public web Bearer token** (`cfg.X.BEARER` — not a per-user secret) + the `ct0` cookie echoed as `x-csrf-token` + `x-twitter-auth-type: OAuth2Session`. Own user id comes from the `twid` cookie (no network call). v1.1 does **not** validate `x-client-transaction-id`, so it's omitted.
- **X bulk unlike (`src/x-unlike.js`) — DOM-click, Feature-1 spirit, select-mode UI (Aug 3 audit: user picks which tweets, not unlike-all).** Floating toolbar on your own `/likes`: "Select" turns tweet clicks into selection toggles (capture-phase interception, Feature-4 pattern), plus "Select all" for everything loaded; "Unlike (n)" then clicks each chosen tweet's native heart (`[data-testid="unlike"]`), tracked by tweet id with the `bwi-x-selected` highlight re-applied on mutation (virtualized timeline recycles nodes), through `queue.js`. No API. **X bulk unfollow (`src/x-unfollow.js`) — DOM-first (rebuilt 2026-08 after the friends-list endpoints died, matching the x-unlike philosophy).** On your **own Following page** (`x.com/<you>/following`) a floating toolbar scans the currently-loaded following rows from the DOM (each row's user id is embedded in its `[data-testid="<id>-unfollow"]` button), checks follow-back via `BWI.xApi`'s `friendships/lookup.json` (the one surviving v1.1 read), lists the non-followers among loaded rows, and unfollows by clicking X's **own** Following button + confirmation sheet — all through `queue.js` (X caps + own daily key — do NOT reuse IG caps — and `DRY_RUN`). "Loaded rows" like bulk-unlike: scroll to load more, rescan.
- **X DOM-only features.** `x-feed.js` forces the chronological Following tab on Home (role=tab + text, once per nav so it doesn't fight the user). `x-hide.js` is a read-only ad filter (`data-testid="placementTracking"` + ad-marker text from `cfg.X.LABELS`; conservative — no touching who-to-follow/trends). `x-keys.js` acts on the **hovered** tweet (X's native keys need keyboard focus) by clicking its inline buttons — `E` like, `Shift+R` reply, `Shift+D` open full-res photo, `Shift+C` copy link. All three: no API, no queue, no writes.
- **Reddit (`reddit-unsave.js`, `reddit-hide.js`).** Unsave (rebuilt 2026-08, Aug 3 audit — the DOM-click build did nothing; select-mode added for the Aug 4 audit: click items to choose, "Select all", **plus** a direct "Unsave all loaded" — two buttons sharing one `confirmTarget` two-click confirm): the DOM is used **only to collect fullnames** (old: `.thing[data-fullname]`; shreddit: `shreddit-post` id/post-id + comment-attr probes, with a shadow-piercing `deepQueryAll` fallback); the unsave itself is the decade-stable legacy JSON API — same-origin `POST /api/unsave` with `id` + modhash (fetched once from `/api/me.json`, old-reddit inline-config scrape as fallback), identical on both hosts. Errors carry `.status` so `queue.js` stops on 429 (plus legacy `RATELIMIT` body detection); unsaved rows fade via `.bwi-unsaved`. Through `queue.js`. Hide: read-only filter on `<shreddit-ad-post>` + the mandated "Promoted" label (`cfg.REDDIT.LABELS`).

**Verify every write actually applied.** A DOM-automation action that clicks and returns without confirming the change is the worst failure mode in this codebase: the queue counts it done, spends the daily budget, clears the selection, and reports "Done — removed N" while nothing happened — and because nothing throws, `isActionBlock` can never halt a run during a rate-limit. Every mutating action must confirm the effect (the row unmounts, the button flips) and **throw** otherwise, with `err.status = 429` when the likely cause is throttling (`x-unlike`, `x-unfollow`, `yt-bulk`). On X specifically the flip is **optimistic** — the heart/button changes before the server answers and reverts if the write is rejected — so both X actions wait ~700ms after the flip and re-check that it stuck before returning success. On Instagram the same rule lives in `ig-api.postFriendship` → `friendshipApplied()`, which distrusts a bare 200 (Instagram answers 200 `{status:"ok"}` with `friendship_status.following` still true) and retries the `/web/` variant; errors from that fallback propagate **untouched** so action-blocks still reach the queue.

**Bulk actions go through one place.** `src/queue.js` is a singleton queue — the only path for bulk actions on **every** platform. `run(items, action, opts)` takes `action` as either a method name on `BWI.api` (Instagram: `"unfollow"` / `"unsave"`) or an **async function** `(item) => Promise` (DOM-automation platforms like YouTube; the function must honor `cfg.DRY_RUN` itself), plus an `opts` override for `minDelay`/`maxDelay`/`sessionCap`/`dailyCap`/`dailyKey`, so each action gets its own throttle and **its own daily budget** (unfollow → `bwi_daily_<date>`, unsave → `bwi_daily_unsave_<date>`, YT Watch Later → `bwi_daily_wl_remove_<date>`, YT unlike → `bwi_daily_unlike_yt_<date>`, X unlike → `bwi_daily_unlike_x_<date>`, X unfollow → `bwi_daily_unfollow_x_<date>`, Reddit unsave → `bwi_daily_unsave_reddit_<date>`); unset fields fall back to the conservative unfollow defaults in `config.js`. It enforces randomized inter-action delays plus session/daily caps (persisted in `chrome.storage.local`) and stops on action-blocks — Instagram (429 / `feedback_required`) and X (429 / error codes 88/326/64/261), both handled by `isActionBlock`. It emits progress events consumed by feature UIs and the popup, and resolves `BWI.api` lazily so it loads on hosts without an API layer. Do not add a second bulk path that bypasses these caps; account safety depends on this throttling. Two consequences of it being a **singleton**: `run()` silently no-ops when busy and `onProgress()` has a single listener slot, so a second feature starting a run would do nothing *and* render the live run's events as its own — every entry point must therefore call `queue.isBusy()` first and bail with a toast (all six do). `DRY_RUN` runs deliberately skip `bumpDailyCount` so a rehearsal can't spend the real budget. Ad-hoc single actions outside the queue (Feature 2's per-row Unfollow) must still check and bump the shared daily counter via `BWI.queueUtil`.

## Conventions that matter

- **Never select by a site's CSS classes** — they are obfuscated and change constantly. Match on ARIA roles (`[role="dialog"]`), **button text**, stable URL shapes (e.g. `a[href*="/p/"]`, `a[href*="watch?v="]`), and — on YouTube — semantic custom-element tag names (`ytd-playlist-video-renderer` etc., which are stable API-like names, unlike class names). All visible-text labels live in `src/config.js` (`LABELS` for Instagram, `YT.LABELS` for YouTube; English only); the confirm-dialog button text and the private-API shape are the things most likely to break when a site changes, so keep them centralized there and in `ig-api.js`.
- **All tunables are in `src/config.js`**: `DRY_RUN`, throttle delays, session/daily caps (including per-action blocks like `UNSAVE`), app IDs, labels. Prefer adding knobs there over hardcoding.
- **Never trigger blocking dialogs** (`window.confirm/alert/prompt`) — they freeze the page. Use inline two-click confirms and `ui.toast` instead.
- **A `MutationObserver` callback must never mutate the subtree it observes without a guard.** A 2026-08 fix round found the identical infinite-observer freeze in `reddit-unsave.js`, `x-unlike.js`, and the since-removed `tiktok-bulk.js` (the observer callback rewrote toolbar `textContent` inside the observed subtree, retriggering itself and hard-freezing the page). The pattern to keep: idempotent DOM setters (only write when the value actually changes), a self-mutation filter (ignore mutations inside `bwi-` UI), and a debounce.
- Injected DOM/CSS is namespaced with a `bwi-` class prefix (`styles.css`, `src/ui.js`) to avoid colliding with Instagram.
- The popup (`popup.html`/`popup.js`) runs in a separate context and cannot touch the in-page `BWI.*` runtime; it talks to the content script only via `chrome.tabs.sendMessage` (`{ type: "bwi-stop" }`) and reads the daily counter directly from `chrome.storage.local`. It **does** load `src/config.js` (the same IIFE) before `popup.js`, so `DAILY_CAP` and the key maps (`STORY_NAV_KEYS`, `YT.KEYS`, `X.KEYS`) come from `BWI.config`; `popup.js` keeps hardcoded fallbacks (150, the default keys) only for the config-less harness — the live values are never duplicated. The popup is a compact per-site **features & shortcuts cheat sheet** (tabs Instagram/YouTube/X/Reddit; copy lives in the `SITES` array in `popup.js`, keys are formatted from config, features whose config toggle is `false` render dimmed with an "off" tag) plus the IG daily counter and Stop. MV3 CSP: no inline `<script>`/handlers in `popup.html`; every `chrome.*` call is guarded so the sheet renders even without the APIs (that's how the file:// harness tests it). Keep the Instagram tab under Chrome's 600px popup ceiling (it is ~550px; the panels area caps at 336px and scrolls).

## Non-goals

Mobile/Firefox, stored credentials, a backend, analytics/telemetry, or any network call to a non-platform host (the privacy disclosures in `PUBLISHING.md`/`PRIVACY.md` promise zero collection — keep them true). Chrome Web Store distribution became a goal in 2026-08: `PUBLISHING.md` is the submission guide, `scripts/package.sh` builds the upload zip, `scripts/gen-icons.js`/`scripts/gen-promo.py` regenerate the icons and store art, and the extension was renamed **Socialfix** (trademark risk killed "Better Web Insta").
