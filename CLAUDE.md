# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, unpacked Manifest V3 Chrome extension with power-user features across **instagram.com, youtube.com, x.com, reddit.com, linkedin.com, and tiktok.com** (see `README.md` for the full user-facing list and `PRD.md` for the roadmap). Each site gets its own `content_scripts` entry in `manifest.json`, loaded only on that host; `config.js`, `queue.js`, and `ui.js` are shared across all hosts (each platform's tunables live in its own `cfg.<PLATFORM>` block). The foundational Instagram features:

1. **Shift-click instant unfollow/remove** in the Following and Followers list modals.
2. A **"doesn't follow you back" subsection** injected into your own profile's Following modal, with throttled bulk unfollow.
3. **Bigger Followers/Following modals** — widened/heightened so there's room for both the native list and the Feature 2 subsection (toggle via `BIGGER_MODALS` in `src/config.js`).
4. **Bulk unsave on the Saved page** — an inline "Select" mode over the saved-post grid; toggle individual tiles, then "Unsave (n)" fully unsaves the selection through the throttled queue.
5. **Keyboard story navigation** — while viewing a story, `H` jumps to the previous user's story and `L` jumps to the next user's story, skipping any remaining frames of the current person (toggle via `STORY_NAV` in `src/config.js`).

Two later features survive: **see-who-unfollowed** (`feature7.js`) and the **enhanced story composer** (`feature9.js`, text + drawing + fit/fill only). They're documented in `README.md` / `PRD.md`.

**Removed as impossible/native on web** (see `FEATURE_FEASIBILITY_REPORT.md`, and Non-Goals in `PRD.md`) — do not re-add: **story repost** (web ships no story-create call; the finalize endpoint is mobile-tier and flags web-cookie sessions), **per-collection unsave** (collection membership is mobile-app-only; web silently full-unsaves), **carousel reorder** (Instagram web now reorders natively), **bio-link editing** and **Emoji Pong** (both mobile-app-only). The story composer's interactive link/poll stickers were cut for the same reason (web configure silently drops them).

### Important correction: "Bulk unlike"

`PRD.md` lists **"Bulk unlike"** in the *Existing Features* table as "Shipped", and commit `bf16c09` reinforces this. **This is misleading.** Bulk unlike is a **native Instagram feature** (Settings → Your activity → Interactions → Likes, where you can multi-select and remove likes). It was **not built by this extension** — there is no bulk-unlike code anywhere in this repo. When the PRD says "same pattern as Bulk Unlike," read that as **"same pattern as bulk unfollow"** (`feature2.js` + `queue.js` + `ig-api.js`), which is the reference implementation for any new bulk action.

## Commands

There is **no build step, no package manager, and no test suite** — it's plain vanilla JS loaded directly as content scripts.

- **Syntax-check after edits:** `node --check src/<file>.js` (and `node -e "JSON.parse(require('fs').readFileSync('manifest.json','utf8'))"` for the manifest). This is the only automated check available.
- **Run / verify:** load unpacked at `chrome://extensions` (Developer mode → Load unpacked → repo root), then exercise on a live, logged-in instagram.com or youtube.com tab. Behavioral verification is manual — there is no way to test against a site's real DOM/API without a logged-in browser session.
- **Safe testing:** set `DRY_RUN: true` in `src/config.js` so every mutating action (IG unfollow/remove/unsave/story upload, YT playlist removals) is logged to the console instead of performed.

## Architecture

Content scripts run in Chrome's **isolated world** and share one `window` object. Everything hangs off a single `window.BWI` namespace; each file does `const BWI = (window.BWI = window.BWI || {})` and attaches its exports (`BWI.config`, `BWI.api`, `BWI.queue`, `BWI.ui`, etc.).

**Load order is significant** and is fixed per-host in `manifest.json` `content_scripts`:

- **instagram.com:** `config → ig-api → queue → ui → feature1 → feature2 → feature3 → feature4 → feature5 → feature7 → feature9`. The `feature6`, `feature8`, `feature10`, and `feature11` slots are intentionally vacant — bio-links (6), story repost (8), carousel reorder (10, along with the former `src/mainworld.js`), and Emoji Pong (11) were removed as impossible/native; files were **not** renumbered.
- **youtube.com:** `config → queue → ui → yt-bulk → yt-keys` (no `ig-api` — the YT modules are pure DOM automation; `queue.js` resolves `BWI.api` lazily so it loads fine without it).
- **x.com:** `config → queue → ui → x-api → x-feed → x-hide → x-keys → x-unlike → x-unfollow`. `x-api.js` exposes `BWI.xApi` (X's private v1.1 web API, cookie-authed); the DOM-only features (`x-feed`, `x-hide`, `x-keys`, `x-unlike`) don't use it.
- **\*.reddit.com:** `config → queue → ui → reddit-unsave → reddit-hide`.
- **linkedin.com:** `config → queue → ui → linkedin-invites → linkedin-hide`.
- **tiktok.com:** `config → queue → ui → tiktok-bulk`.

There is no MAIN-world content script anywhere. A file may only reference `BWI.*` symbols defined by an earlier file in its host's entry. If you add a file or a cross-file dependency, update the relevant order. Shared DOM helpers used by more than one feature (e.g. `ui.dialogTitleIs`, `ui.findScrollContainer`, `ui.toast`) live in `src/ui.js`.

The features are deliberately built on **different strategies**:

- **Feature 1 (`src/feature1.js`) uses no API at all.** A capture-phase click listener flags a Shift+click on a row's trigger button, then a `MutationObserver` auto-clicks the destructive button in Instagram's *own* confirmation dialog once it appears (<100ms, looks instant). This rides Instagram's native flow, so it's the most resilient part. It never calls the private API.
- **Feature 2 (`src/feature2.js` + `src/ig-api.js`) uses Instagram's private web API.** `ig-api.js` calls `/api/v1/friendships/...` same-origin with `credentials: 'include'`, so the session cookies are sent automatically — there is no login/auth code. It paginates the full following + followers lists, computes the set difference, and unfollows. This is the fragile part: endpoint paths and required headers (`X-IG-App-ID`, `X-CSRFToken`, `X-IG-WWW-Claim`) are all isolated in `ig-api.js`. Detection does **not** depend on the URL changing to `/<user>/following/` (Instagram opens the list as a client-side modal and may not push that URL); it identifies the modal by ARIA role + title text and confirms ownership via the profile path segment.
- **Feature 3 (`src/feature3.js`) is pure CSS/DOM, no API.** It finds the Followers/Following list dialog (any profile) and tags it + its scroll container with `bwi-big-*` classes; `styles.css` does the resizing with `!important` so it survives React re-renders. Because Instagram virtualizes the list, it dispatches a `resize` event after tagging so the windowing recomputes visible rows.
- **Feature 4 (`src/feature4.js` + `src/ig-api.js`) uses the private API + the shared queue.** On your own Saved page it injects a toolbar above the post grid with a "Select" toggle. In select mode a capture-phase click listener intercepts tile clicks (blocking navigation) and tracks the selection **by post shortcode** (not DOM node — the grid is virtualized and recycles nodes on scroll, so overlays are re-applied on mutation). The numeric media id needed by `/api/v1/media/{id}/unsave/` is derived locally from the shortcode via `api.shortcodeToMediaId()` (base64 decode — no extra network read), and the unsave calls run through `queue.js`.
- **Feature 5 (`src/feature5.js`) is pure DOM, no API — closest in spirit to Feature 1.** A capture-phase `keydown` listener (active only when `location.pathname` starts with `STORY_NAV_PATH_PREFIX`, i.e. `/stories/`) maps `H`/`L` (from `STORY_NAV_KEYS`) to previous/next *user* and clicks Instagram's own on-screen control rather than reconstructing tray order. Per repo convention the control is resolved by stable URL shape first — the dimmed neighbor-story anchors `a[href^="/stories/"]` flanking the active story, picking the visible one nearest viewport center on the requested side — and falls back to the round chevron buttons by aria-label (`LABELS.storyPrev`/`storyNext`). It no-ops on modifier keys and when focus is in an input/textarea/contenteditable (so `H`/`L` in the story reply box are untouched), and toasts "No previous/next story" when no control is found. The keys deliberately differ from the arrow keys, which step one frame at a time. **`H`/`L` (not the PRD's originally-proposed `J`/`K`) are intentional** — horizontal left/right mirrors the spatial direction of story navigation.
- **Feature 7 (`src/feature7.js`) — see-who-unfollowed.** Read-only: on your own Followers modal it snapshots your follower set to `chrome.storage.local` and diffs against the prior snapshot to surface who left. Reuses `ig-api.js`'s follower pagination; correctly bypasses `queue.js` (read-only, not a mutation).
- **Feature 9 (`src/feature9.js`) — enhanced story composer.** A self-contained canvas composer (movable text + freehand drawing + fit/fill) that rasterizes everything into a JPEG and posts it via the private story-upload core in `ig-api.js` (`ruploadPhoto` → `configureToStory`). A mutating write: honors `DRY_RUN` and its own daily budget (`cfg.STORY.DAILY_KEY`/`DAILY_CAP`). Interactive link/poll stickers were removed — the web configure endpoint silently drops them.
- **YouTube bulk-remove (`src/yt-bulk.js`) — pure DOM automation, Feature-1 spirit.** On `/playlist?list=WL|LL` it injects a Select toolbar; each queued removal opens the row's own ⋮ menu (aria-label) and clicks the native "Remove from …" item (visible text from `cfg.YT.LABELS`), riding YouTube's real flow — no InnerTube/SAPISIDHASH. Selection is tracked by **videoId** (parsed from each row's `/watch?v=` link), not DOM node. Runs through `queue.js` with a **function action** and deliberately slow 5–8 s delays (YouTube processes deletions async; faster makes items reappear). Separate daily keys per playlist (`bwi_daily_wl_remove_` / `bwi_daily_unlike_yt_`). The function action must honor `cfg.DRY_RUN` itself (there's no API layer to do it). Handles SPA navigation via `yt-navigate-finish` + MutationObserver.
- **YouTube shortcuts (`src/yt-keys.js`) — Feature-5 spirit.** Capture-phase `keydown` on watch pages clicking native buttons by aria-label/visible text: `E` Like, `Shift+E` Save-to-playlist, `Shift+U` Subscribe, `N` comment box (`cfg.YT.KEYS`). Fills ONLY the gaps in YouTube's native shortcut set — do not rebuild K/J/L/F/M/etc. No queue (single non-destructive actions). Selectors use semantic custom-element tags (`ytd-watch-metadata`, `ytd-menu-service-item-renderer`) — stable for years, unlike class names — plus aria-labels and text.
- **X private API (`src/x-api.js` → `BWI.xApi`).** Same-origin to `x.com/i/api/1.1/…` with `credentials:'include'`; authed by the static **public web Bearer token** (`cfg.X.BEARER` — not a per-user secret) + the `ct0` cookie echoed as `x-csrf-token` + `x-twitter-auth-type: OAuth2Session`. Own user id comes from the `twid` cookie (no network call). Paginates following (`friends/list.json`), diffs follow-back via batched `friendships/lookup.json` (cheaper than paging all followers), unfollows via `friendships/destroy.json`. v1.1 does **not** validate `x-client-transaction-id`, so it's omitted. `fetchAllFollowing` throws on an incomplete paginate (same guarantee as `ig-api`).
- **X bulk unlike (`src/x-unlike.js`) — DOM-click, Feature-1 spirit.** Floating toolbar on your own `/likes`; unlikes currently-loaded tweets by clicking each native heart (`[data-testid="unlike"]`), tracked by tweet id, through `queue.js`. No API. **X bulk unfollow (`src/x-unfollow.js`)** — launcher → panel that scans non-followers via `BWI.xApi` and unfollows through `queue.js` (X caps + own daily key — do NOT reuse IG caps).
- **X DOM-only features.** `x-feed.js` forces the chronological Following tab on Home (role=tab + text, once per nav so it doesn't fight the user). `x-hide.js` is a read-only ad filter (`data-testid="placementTracking"` + ad-marker text from `cfg.X.LABELS`; conservative — no touching who-to-follow/trends). `x-keys.js` acts on the **hovered** tweet (X's native keys need keyboard focus) by clicking its inline buttons — `E` like, `Shift+R` reply, `Shift+D` open full-res photo, `Shift+C` copy link. All three: no API, no queue, no writes.
- **Reddit (`reddit-unsave.js`, `reddit-hide.js`).** Unsave: floating toolbar on the Saved page; **old.reddit.com** is the robust primary (`.thing[data-fullname]` + an anchor whose text is "unsave"), new/shreddit Reddit is best-effort via a `deepQueryAll` that **pierces shadow roots** (overflow menu → "Remove from saved"). Items re-located by fullname; through `queue.js`. Hide: read-only filter on `<shreddit-ad-post>` + the mandated "Promoted" label (`cfg.REDDIT.LABELS`).
- **LinkedIn (`linkedin-invites.js`, `linkedin-hide.js`).** Most automation-hostile host — everything text-matched, **conservative caps**, and a hard stop the instant a restriction/CAPTCHA banner appears (`cfg.LINKEDIN.LABELS.restrictionMarkers`, checked before every action and shaped as a 429 so `queue.isActionBlock` halts the run). Withdraw: on the Sent-invitations page, click a row's "Withdraw" then the inline-popover "Withdraw"; always acts on the first still-present row (the list re-flows). Hide: read-only "Promoted" filter with **zero-width-char-stripping** text normalization (LinkedIn injects them to defeat matchers).
- **TikTok (`tiktok-bulk.js`).** Bulk remove from your own **Liked/Favorites** tabs by **pure DOM** — NOT the private `commit/item/digg` API (which is X-Bogus kill-switch-fragile and needs MAIN-world page state). Per item: click the grid tile → wait for the video modal → click the like/favorite toggle off (aria-label; skip if `aria-pressed="false"` so it never re-likes) → close (`data-e2e="browse-close"`), through `queue.js`. Tab + tile hooks are `data-e2e`/aria/text (`cfg.TIKTOK`) — the likeliest maintenance point given TikTok's obfuscation. **Deferred (see PRD):** LinkedIn bulk-remove-connections (destructive/highest-risk) and the TikTok private-API bulk-unlike — build only with a live DRY_RUN pass.

**Bulk actions go through one place.** `src/queue.js` is a singleton queue — the only path for bulk actions on **every** platform. `run(items, action, opts)` takes `action` as either a method name on `BWI.api` (Instagram: `"unfollow"` / `"unsave"`) or an **async function** `(item) => Promise` (DOM-automation platforms like YouTube; the function must honor `cfg.DRY_RUN` itself), plus an `opts` override for `minDelay`/`maxDelay`/`sessionCap`/`dailyCap`/`dailyKey`, so each action gets its own throttle and **its own daily budget** (unfollow → `bwi_daily_<date>`, unsave → `bwi_daily_unsave_<date>`, YT Watch Later → `bwi_daily_wl_remove_<date>`, YT unlike → `bwi_daily_unlike_yt_<date>`, X unlike → `bwi_daily_unlike_x_<date>`, X unfollow → `bwi_daily_unfollow_x_<date>`); unset fields fall back to the conservative unfollow defaults in `config.js`. It enforces randomized inter-action delays plus session/daily caps (persisted in `chrome.storage.local`) and stops on action-blocks — Instagram (429 / `feedback_required`) and X (429 / error codes 88/326/64/261), both handled by `isActionBlock`. It emits progress events consumed by feature UIs and the popup, and resolves `BWI.api` lazily so it loads on hosts without an API layer. Do not add a second bulk path that bypasses these caps; account safety depends on this throttling.

## Conventions that matter

- **Never select by a site's CSS classes** — they are obfuscated and change constantly. Match on ARIA roles (`[role="dialog"]`), **button text**, stable URL shapes (e.g. `a[href*="/p/"]`, `a[href*="watch?v="]`), and — on YouTube — semantic custom-element tag names (`ytd-playlist-video-renderer` etc., which are stable API-like names, unlike class names). All visible-text labels live in `src/config.js` (`LABELS` for Instagram, `YT.LABELS` for YouTube; English only); the confirm-dialog button text and the private-API shape are the things most likely to break when a site changes, so keep them centralized there and in `ig-api.js`.
- **All tunables are in `src/config.js`**: `DRY_RUN`, throttle delays, session/daily caps (including per-action blocks like `UNSAVE`), app IDs, labels. Prefer adding knobs there over hardcoding.
- **Never trigger blocking dialogs** (`window.confirm/alert/prompt`) — they freeze the page. Use inline two-click confirms and `ui.toast` instead.
- Injected DOM/CSS is namespaced with a `bwi-` class prefix (`styles.css`, `src/ui.js`) to avoid colliding with Instagram.
- The popup (`popup.html`/`popup.js`) runs in a separate context and cannot touch `BWI.*`; it talks to the content script only via `chrome.tabs.sendMessage` (`{ type: "bwi-stop" }`) and reads the daily counter directly from `chrome.storage.local`. `DAILY_CAP` is duplicated in `popup.js` — keep it in sync with `config.js`.

## Non-goals

Web Store distribution, mobile/Firefox, stored credentials or a backend. Personal use, load-unpacked only.
