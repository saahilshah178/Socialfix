# Better Web Insta — Feature Feasibility & Implementation Plan

> Definitive planning report for the extension owner and the future model that will implement approved features.
> Verdicts below honor adversarial refutation: where a `verify` pass produced a `revisedVerdict`, that revision is the final word.
> The prime directive: **never greenlight a feature that is impossible for platform reasons** (the emoji-pong / web-bio-link lesson).

---

## 1. Executive summary

**22 features researched, across 6 platforms. Final verdict counts:**

| Verdict | Count | Meaning |
|---|---|---|
| **FEASIBLE** | 14 | Build it. Proven mechanism, cookie-authed web path or pure DOM. |
| **FRAGILE** | 3 | Buildable but high-maintenance or elevated ban-risk. Build with extra care + DRY_RUN. |
| **IMPOSSIBLE** | 3 | Do **not** build. Platform-level wall, not a code problem. |
| **NATIVE_EXISTS** | 2 | Do **not** build. The platform already ships it. |

### Most important takeaways

1. **The web/mobile private-API wall is real and it recurs.** Two of the three IMPOSSIBLE features (IG story-repost, IG collection-scoped-unsave) die for the *exact same reason* that killed bio-links and emoji-pong: the write endpoint lives on the mobile-app private-API tier, which rejects browser-cookie sessions. One IG feature already in the tree (`feature8.js` enhanced story composer) is half-impossible for this reason — its interactive stickers must be cut.
2. **The safest, highest-value expansion is "bulk cleanup" on new platforms.** Bulk-unlike / bulk-unfollow / bulk-unsave / bulk-remove patterns port cleanly to X, TikTok, YouTube, Reddit, and LinkedIn — all reuse `queue.js` + an `ig-api.js`-style module, and most have a **native-flow DOM-click fallback** (the Feature-1 pattern) that sidesteps request-signing entirely.
3. **DOM-click > private API wherever both exist.** For every "bulk remove" feature, riding the platform's own UI button through `queue.js` is more resilient than hand-rolling signed requests, and dodges the anti-bot signing schemes (TikTok X-Bogus, X client-transaction-id, YouTube SAPISIDHASH). Prefer it.
4. **"Hide ads / force chronological" are trivially safe** — pure read-only DOM filtering, zero account-mutation, no queue needed, no ban risk. Good low-effort wins.
5. **LinkedIn is the one genuinely hostile host.** Its features are technically feasible but carry the highest ban-risk profile of any platform here; treat all LinkedIn write-actions as FRAGILE and gate them behind conservative caps + immediate stop-on-restriction.

### 🚫 DO NOT BUILD — impossible on web (the anti-emoji-pong list)

| Feature | Platform | One-line platform reason |
|---|---|---|
| **Story repost** (repost another user's photo story) | Instagram | The web client ships **no** story-create call at all; the only working finalize endpoint (`/api/v1/media/configure_to_story/`) is mobile-app-tier and rejects web-cookie sessions (`login_required`) — firing it risks getting the session flagged/logged out. |
| **Collection-scoped unsave** (remove from ONE collection, not fully unsave) | Instagram | Collection membership management is mobile-app-only per IG's own Help Center; `removed_collection_ids` on the web save endpoint is either rejected or silently ignored (fully unsaves instead). No web-compatible signed path. |
| **See mutual follows** (people you + another user both follow) | TikTok | The follower/following list endpoint (`/api/user/list/`) is gated by client-side `X-Bogus`/`X-Gnarly` signatures generated by an obfuscated in-page VM, not derivable from cookies; clicking the follower count while logged out even throws the login modal. Requires shipping reverse-engineered crypto that breaks every TikTok deploy. |

### 🚫 DO NOT BUILD — the platform already ships it (NATIVE_EXISTS)

| Feature | Platform | Reason |
|---|---|---|
| **Carousel reorder** (reorder images before publish) | Instagram | IG's own desktop web composer already supports drag-and-drop reordering of the thumbnail tray before publish. The built `mainworld.js` request-interception solves a problem the native UI already solves. |
| **Keyboard post navigation** (j/k next/prev) | Reddit | New Reddit ships j/k/Enter/x + 13 more shortcuts natively (Shift+? to view). Building it would only create conflicting listeners. |

## 2. Instagram — remaining features

These are already partially built in-tree. Framing is **verify/fix** vs **rebuild** vs **rip out**.

### 2.1 See-who-unfollowed — ✅ FEASIBLE (confidence: HIGH) — *verify & harden*

- **Verdict / mechanism:** FEASIBLE. Read-only private web API — the *same* `/api/v1/friendships/{userId}/followers/` endpoint Feature 2 already paginates. No signing, no mobile tier.
- **Status:** Already implemented as `src/feature7.js`. This is a **verify-and-harden** job, not a build.
- **Implementation hooks:**
  - `GET https://www.instagram.com/api/v1/friendships/{userId}/followers/?count=100&max_id={cursor}`
  - Headers (all reproducible from page JS, already in `ig-api.js`): `X-IG-App-ID: 936619743392459`, `X-CSRFToken` (from `csrftoken` cookie), `X-IG-WWW-Claim: 0` (echoed from `x-ig-set-www-claim`).
  - Paginate on `next_max_id`; stop when null.
  - Storage: `bwi_followers_snap_{ownId}` (snapshot `{ts, pks:[...], users:{...}}`), `bwi_unfollowers_{ownId}` (log).
- **Fits conventions:** Read-only → **correctly bypasses `queue.js`** (queue is for mutations only). Reuses `ig-api.js` `fetchAllList`. No DRY_RUN needed (non-mutating).
- **Risk:** LOW. Not a ban vector. Three correctness caveats to fix, not platform blockers:
  1. Re-paginating the full follower list every visit is real request volume — throttle/cache for very large accounts (add a min-interval-between-snapshots knob to `config.js`).
  2. "Unfollowed" is *inferred* — it conflates true unfollows with deactivated / banned / blocked / went-private accounts. Label the UI honestly ("no longer following you or deactivated").
  3. The existing truncation guard (`prev>20 && current==0`) only catches a total-empty failure; a **partial** fetch that returns half the list produces false unfollows. Harden: reject the diff if the fetch didn't reach a clean end-of-list terminator.
- **Build sketch:** Read `feature7.js`, confirm endpoint/headers still match `ig-api.js`, add the min-interval snapshot cap + partial-fetch guard, correct the UI label. Verify live against your own account with a small follower delta.

### 2.2 Enhanced story composer — ⚠️ FRAGILE (confidence: MEDIUM) — *rebuild scope: cut the stickers*

- **Verdict / mechanism:** FRAGILE. **Bimodal.** The composer core is genuinely feasible; the interactive stickers are effectively impossible from a cookie content script.
- **Status:** Built as `src/feature8.js` + `ig-api.js` `configureToStory`/`configureToStoryApp`, unverified.
- **What WORKS (keep):**
  - **Binary upload:** `rupload_igphoto` two-step upload runs same-origin with `credentials:'include'` + web app-id — this is the exact path the mobile-web PWA's real "Add to story" uses. Reproducible from a content script.
  - **Client-side rasterization:** text + freehand drawing burned into the JPEG before upload — **zero API dependency**, trivially feasible.
  - **Fit/fill:** pure canvas math — fine.
- **What is BROKEN (cut it):**
  - `story_sticker_ids` + `tap_models` (link sticker `link_sticker_default`, poll `polling_sticker_v2`) on the plain web `/create/configure_to_story/` path are **silently dropped** — the story posts successfully but the sticker never appears (confirmed: dilame/instagram-private-api #1724). IG's own web client ships no UI for these, strong first-party evidence the web app-id session isn't authorized to honor them.
  - The `configureToStoryApp()` app-tier fallback (`/api/v1/media/configure_to_story/` with `signed_body`) **cannot rescue it**: that endpoint checks for a mobile-app session (mobile app-id `567067343352427`, Instagram Android User-Agent, device seeds). A page-JS `fetch` **cannot set the User-Agent header** (Forbidden header per Fetch spec) and the cookie is bound to the web app, not a mobile session. The `signed_body` "SIGNATURE." trick passes (IG stopped HMAC-verifying) but a passing signature does not grant app-tier authorization.
- **Risk:** MEDIUM. Live risk if DRY_RUN off: interactive stickers silently missing (could go unnoticed), or a 400 on unexpected `tap_models`. Repeatedly hitting the app-tier fallback from a bare cookie session risks tripping `challenge_required`/`checkpoint_required`.
- **Build sketch (rebuild scope):** Strip `configureToStoryApp()` and all `tap_models`/`story_sticker_ids` payload code out of the live path (leave a `DRY_RUN`-only stub if you want to keep experimenting). Ship the composer as: upload + client-rasterized text/drawing + fit/fill only. Route the single configure write through `queue.js` (write from an unusual context → must ride the caps). Advertise honestly: "text + drawing stories," **not** "poll/link stickers."
- **Low-confidence check to run:** With DRY_RUN on, capture the real `rupload_igphoto` + `/create/configure_to_story/` requests from a manual mobile-web "Add to story" in DevTools, diff against `configureToStory()`'s body, and confirm the plain (text/drawing-only) post succeeds live before trusting it.

### 2.3 Story repost — 🚫 IMPOSSIBLE — *rip it out*

See DO-NOT-BUILD table. Built as `src/feature9.js` (unverified). **Action: remove the live path.** If `configureToStoryApp()` is wired as a fallback, it is actively dangerous — it fires a mobile private-API call from a browser cookie session, whose documented failure mode is not a 400 but the **session getting flagged / logged out**. Rip it out; keep the composer work from 2.2 that is salvageable (upload + rasterization) if any is shared.

### 2.4 Carousel reorder — 🚫 NATIVE_EXISTS — *retire the interception*

See NATIVE_EXISTS table. Built as `src/mainworld.js` / `feature10.js` MAIN-world interception of `configure_sidecar`. **Action: retire it** and instead point users at IG's own drag-to-reorder thumbnail tray (or confirm it's present and simply undiscovered). The interception is unverified (`CAPTURE-AND-ADJUST` per its own comments), risks silently no-op'ing or breaking the whole post submission, and any client-side tamper IG detects (content-length mismatch, added signed fields) could flag the account.

### 2.5 Collection-scoped unsave — 🚫 IMPOSSIBLE — *do not start*

See DO-NOT-BUILD table. Not in-tree; never begin. Any attempt from web cookies will 400, silently fully-unsave, or (if you chase mobile signing) risk action-blocks.

## 3. Per-platform planned features

All new-platform work reuses the house architecture: one `ig-api.js`-style endpoint module per host, all mutations through `queue.js` with a **dedicated daily-cap key**, ARIA/text/URL selectors only, labels in `config.js`, `DRY_RUN` respected. Each new host is a module loaded only when its host is active.

### Twitter / X

#### 3.1 Bulk unlike — ✅ FEASIBLE (MEDIUM) — DOM-click primary

- **Mechanism:** Native heart-button clicks on your own `/likes` tab (primary, resilient), with a private GraphQL `UnfavoriteTweet` fallback.
- **Hooks:**
  - **DOM (primary):** own `x.com/<user>/likes` timeline; click the "Unlike"/"Liked" heart (`aria-label`), scroll to load more. Rides X's own client code → inherits whatever CSRF/transaction-id headers X requires.
  - **API (fallback):** `POST graphql/{queryId}/UnfavoriteTweet` body `{variables:{tweet_id}, queryId}`; enumerate via `graphql/{queryId}/Likes` (`{userId,count,cursor}`). Headers: `Authorization: Bearer <static public web token>` (in every page load), `X-Csrf-Token: <ct0 cookie>`, `Content-Type: application/json`, `credentials:'include'`. **Correction to prior evidence:** current tools DO send `X-Client-Transaction-Id` — do not assume it's unneeded; it's computed client-side (swyxio/XClientTransactionJS) with no server secret, so reproducible, but the DOM path avoids it entirely. Own-Likes enumeration is intact on web (June 2024 change only hid *others'* likes).
- **Conventions:** `queue.js` with own key `bwi_daily_unlike_x_<date>`; isolate all query-ids/token in an `x-api.js` module; two-click inline confirm before a large batch (mass irreversible action). DRY_RUN logs.
- **Risk:** MEDIUM. ~500 unlikes/15min before 429; blocks 15–60 min first offense. Conservative caps + stop-on-429.
- **Build sketch:** DOM-click loop through `queue.js` on the `/likes` page; keep the GraphQL module as an optional faster path behind a config flag.

#### 3.2 Bulk unfollow non-followers — ✅ FEASIBLE (HIGH)

- **Mechanism:** Private web REST v1.1, cookie-authed same-origin. Two independent 2026-maintained MV3 extensions (kysoog/x-unfollowers, K4nes/X-Unfollower) do exactly this; source-verified.
- **Hooks (host is `x.com/i/api/1.1/`, NOT `api.x.com`):**
  - `GET x.com/i/api/1.1/friends/list.json?count=200&cursor=...` (following)
  - `GET .../followers/list.json` (followers)
  - `GET .../friendships/lookup.json?user_id=<up to 100 ids>` (batch follow-back check — compute non-followers via lookup, avoids full follower paging)
  - `POST .../friendships/destroy.json` (unfollow)
  - Headers: `authorization: Bearer <static public web token>`, `x-csrf-token: <ct0 cookie>`, `x-twitter-auth-type: OAuth2Session`, `credentials:'include'`. **No `x-client-transaction-id` needed** — v1.1 doesn't validate it (K4nes even sends a random fake one).
- **Conventions:** `queue.js` with own key `bwi_daily_unfollow_x_<date>`; **do not reuse IG unfollow caps** — X limits differ.
- **Risk:** MEDIUM–HIGH by volume. `friends/list.json` ~15 req/15min; safe unfollow ceiling ~50–100/day, 400+/day → write-restricted 24–72h. Pacing matters as much as volume.
- **Build sketch:** `x-api.js` module for the 4 endpoints + lookup-based diff; all destroys through `queue.js`; two-click confirm.

#### 3.3 Chronological "Following" feed enforcer — ✅ FEASIBLE (HIGH)

- **Mechanism:** Pure DOM. No API, no CSRF, no queue.
- **Hooks:** target the Home tablist by `role="tab"` + visible text "Following" (not classes); `element.click()` it. X does NOT persist the choice (resets to "For You" every refresh — that's the gap). **Correction:** as of Nov 2025 the Following feed is itself algorithmically ranked by default; true chronological now needs a **second** DOM click — open the sort control next to "Following" and pick "Recent"/"Latest" (this option survives on desktop web though removed from the apps). Still pure DOM.
- **Conventions:** MutationObserver to re-apply on SPA navigation; optional `localStorage` flag to respect a manual user override. Living proof: mustafaer/twitter-default-following-tab (v2.0.0, Dec 2025).
- **Risk:** MINIMAL. Mirrors a manual click; zero ban risk. Only fragility: tab markup churn (mitigate with position/ARIA detection).

#### 3.4 Keyboard shortcuts parity — ✅ FEASIBLE (HIGH)

- **Mechanism:** Content-script capture-phase `keydown` → clicks X's own native buttons (Delete/Quote/Pin via the tweet overflow menu, resolved by `aria-label`/text). Never calls the API — X's page code fires its own signed GraphQL. Identical to IG Feature 1.
- **Hooks:** delete = `aria-label="Delete"`; quote = aria-label containing "Quote"; pin via overflow menu item text; download photo = `pbs.twimg.com` img src + `:orig`. Existence proof: Twitter Shortcut Plus (r7kamura).
- **Conventions:** keys + labels in `config.js`; no-op in inputs/contenteditable; single user-initiated clicks → no `queue.js`, no ban risk. CSP doesn't govern isolated-world content scripts.
- **Risk:** LOW. One fragile subset: **video** download (HLS/MSE behind `blob:` URLs — no plain src; would need m3u8 interception). Ship photo-download + action shortcuts; treat video download as out of scope or best-effort.

#### 3.5 Hide promoted / algorithmic content — ✅ FEASIBLE (HIGH)

- **Mechanism:** Pure read-only DOM filter. Nothing sent to X → zero ban/rate-limit exposure, no queue.
- **Hooks (data-testid is a semi-stable non-obfuscated hook, analogous to IG ARIA):** `article[data-testid="tweet"]` containing an "Ad"/"Promoted" text node; `div[data-testid="placementTracking"]` (promoted wrapper — remove nearest ancestor); `div[data-testid="trend"]` (promoted trend); `div[data-testid="UserCell"]` (promoted who-to-follow); `aside[aria-label="Subscribe to Premium"]` (nag). Ad-marker fallback: fixed SVG `d` path strings for the ad-disclosure glyph. Re-run on scroll + MutationObserver.
- **Conventions:** put the "Ad"/"Promoted" marker strings in `config.js` LABELS (X flips this text + localizes it — the one maintenance point). Not free natively (removing ads is behind X Premium) → genuine value-add.
- **Risk:** LOW. Maintenance-only selector churn.

### TikTok

#### 3.6 Bulk unlike (own Liked list) — ✅ FEASIBLE (MEDIUM)

- **Mechanism:** Private web API, same-origin from page context with cookies. **No X-Bogus/X-Gnarly needed** for these two endpoints (confirmed: gabireze/tiktok-all-liked-videos-remover, live, maintained into Feb 2026, never added signing).
- **Hooks:**
  - `GET https://www.tiktok.com/api/favorite/item_list/?aid=1988&count=30&cursor=...&secUid=<yours>&needPinnedItemIds=true&post_item_list_request_type=0` (enumerate; `accept: */*` only)
  - `POST https://www.tiktok.com/api/commit/item/digg/?aid=1988&aweme_id=<id>&type=0&app_name=tiktok_web&device_platform=web_pc&verifyFp=<cookie s_v_web_id>&msToken=<cookie msToken>` with header `tt-csrf-token` (unlike; `type=0`)
  - Read `secUid`/`csrfToken` **defensively** from page state (`SIGI_STATE` / `window.__UNIVERSAL_DATA_FOR_REHYDRATION__` — feature-detect multiple globals, don't hardcode). Own liked list is enumerable for the authenticated owner; the privacy toggle only hides likes from *other* viewers.
  - **Must run in MAIN world** (page context) to inherit CSRF/session state — use the existing `mainworld.js` injection pattern.
- **Conventions:** `queue.js` key `bwi_daily_unlike_tiktok_<date>`; `tiktok-api.js` module; DRY_RUN.
- **Risk:** MEDIUM. ~100/hr before a ~1-hour soft-block (reference extension detects this). **Kill-switch risk:** if TikTok ever enables X-Bogus enforcement on in-session `digg`/`item_list`, this breaks — fragile like the IG friendships API, but not impossible today.
- **Low-confidence check:** In DevTools on your own Liked tab, confirm a manual unlike still fires `commit/item/digg` without an `X-Bogus` query param before trusting the live call.

#### 3.7 Bulk remove favorites/collections — ✅ FEASIBLE (MEDIUM)

- **Mechanism:** Pure DOM automation — **no API call, no signing.** Drives the UI like a user (Feature 1/5 pattern). Reference: gabireze/tiktok-all-favorite-videos-remover (~8k users, 4.5★, live).
- **Hooks (flow):** go to own profile → Favorites tab → open first favorite → loop: click heart-toggle, click next-arrow, until exhausted → close. **Do NOT copy the reference's obfuscated selectors** (`[class*="PFavorite"]`, `[class*="DivPlayerContainer"]`, `[data-e2e="undefined-icon"]`). Per repo rules, resolve: Favorites tab by visible text / `aria-selected` tab role; first tile by first playable element under the Favorites grid; heart by `aria-label`/`aria-pressed`; `[data-e2e="arrow-right"]` and `[data-e2e="browse-close"]` (data-e2e hooks are acceptably stable, prefer them over class matching).
- **Conventions:** per-item click through `queue.js` (no native multi-select exists); throttle + stop-on-block.
- **Risk:** MEDIUM. Slow/flaky on very large libraries; occasional ~1hr rate-limit pauses, no bans reported. Scope first pass to the flat Favorites tab; extend to named collections only after confirming the same per-item toggle affordance there.

#### 3.8 See mutual follows — 🚫 IMPOSSIBLE — do not build (see §1 table).

### Reddit

#### 3.9 Bulk unsave — ✅ FEASIBLE (HIGH)

- **Mechanism:** DOM automation (preferred, Feature-1 style) with a cookie+modhash private-API fallback. Not mobile-gated.
- **Hooks:**
  - **old.reddit.com/prefs/saved (recommended primary — flat, text-selector surface):** anchor with `innerText === 'unsave'` in each action row ("delete from saved" variant for comments).
  - **New/shreddit Reddit:** "Remove from saved" under the post overflow menu — inside **shadow DOM** (`shreddit-post` web components) → content script must **pierce shadow roots**, not plain `querySelectorAll`; two-step (open menu, then click item).
  - **API fallback:** `POST https://www.reddit.com/api/unsave` body `id=<fullname>&uh=<modhash>`, cookie-authed, **no OAuth**; modhash scraped from the logged-in page config JSON. DOM path avoids needing modhash at all.
- **Conventions:** `queue.js` (randomized delay + caps + stop-on-block); re-locate items by post fullname after each scroll/reload (virtualized list — Feature-4 discipline). Text labels in `config.js`.
- **Risk:** LOW–MEDIUM. 429 on rapid bursts; historical ~1000-item pagination cap on the saved listing (completeness edge). Runs on the user's own logged-in session so the 2026 old-reddit login requirement is irrelevant.

#### 3.10 Hide promoted posts — ✅ FEASIBLE (HIGH)

- **Mechanism:** Pure read-only DOM filter. No mutation, no API, works logged-out, no queue, zero ban risk.
- **Hooks:** detect via the **mandated visible "Promoted" label** (Reddit's 2026 ad policy requires a non-removable Promoted tag) / the semantic `shreddit-ad-post` element on new Reddit. MutationObserver for infinite scroll. **Do NOT use** `.promotedlink` class or `data-google-query-id` (obfuscated/legacy, churns weekly, violates repo rules).
- **Conventions:** marker text in `config.js` LABELS.
- **Risk:** LOW. Selector-text churn only.

### YouTube

#### 3.12 Bulk-remove Watch Later — ✅ FEASIBLE (HIGH)

- **Mechanism:** DOM automation (primary) — proven shipping category (YT Watch Later Assist, TidyWL, etc.). Private InnerTube path exists but is more fragile.
- **Hooks:**
  - **DOM:** on the WL playlist page, rows are `ytd-playlist-video-renderer`; per-row three-dot resolved by `aria-label` (verify "Action menu" live); menu item matched by **visible text** "Remove from Watch later" (locale-dependent → `config.js`). No native "remove all" — loop per item.
  - **API (optional):** `POST https://www.youtube.com/youtubei/v1/browse/edit_playlist?key=<INNERTUBE_API_KEY>`, body `{context:<ytcfg INNERTUBE_CONTEXT>, playlistId:'WL', actions:[{action:'ACTION_REMOVE_VIDEO', setVideoId:<per-item>}]}`, auth header `Authorization: SAPISIDHASH <ts>_<sha1(ts+' '+SAPISID+' '+origin)>` from the `SAPISID`/`__Secure-3PAPISID` cookie. `setVideoId` (≠ videoId) read per-item from a prior `browse` call. All reproducible from a content script but reverse-engineered/brittle.
- **Conventions:** `queue.js` key `bwi_daily_wl_remove_<date>`. **Critical:** YouTube processes deletions async — firing too fast makes videos reappear on refresh; real tools use 5–8s inter-item delays. Use conservative queue delays.
- **Risk:** LOW–MEDIUM. 429 friction, not bans. DOM path more resilient (repo convention).

#### 3.13 Bulk unlike (Liked videos playlist) — ✅ FEASIBLE (HIGH)

- **Mechanism:** Same as 3.12 but playlist `LL`. DOM per-item "Remove from liked videos" (Feature-1 spirit). Proven by live extensions + Greasyfork scripts (2026).
- **Hooks:** `/playlist?list=LL`; three-dot resolved by `aria-label` (not obfuscated classes); popup item matched by **visible text** "Remove from liked videos" (NOT positional `lastElementChild`). Wait ~100ms after opening menu. InnerTube `edit_playlist` with `playlistId:'LL'` is the faster-but-fragile alternative (adds SAPISIDHASH — not needed).
- **Conventions:** `queue.js` key `bwi_daily_unlike_yt_<date>`; incremental scroll/re-query (virtualized list). No native bulk-remove exists (Google Support threads confirm) → genuine gap.
- **Risk:** LOW–MEDIUM. Same as 3.12.

#### 3.14 Keyboard shortcuts (fill gaps) — ✅ FEASIBLE (HIGH)

- **Mechanism:** Content-script capture-phase `keydown` → clicks native Like/Save/Comment/Subscribe buttons (resolved by `aria-label`/visible text). YouTube ships player shortcuts (K/J/L/F...) but omits these. Identical to IG Feature 5/1. **No InnerTube needed** — a single native click delivers it; the API path in prior evidence is not load-bearing.
- **Hooks:** bind bare keys via an injected page-context keydown listener (Chrome's declarative `commands` API requires a modifier — irrelevant here; content-script listeners bind bare keys freely). Target buttons by aria-label/text.
- **Conventions:** keys + labels in `config.js`; no-op in inputs; single actions on own account → no queue, no ban risk.
- **Risk:** LOW. Only genuine gaps worth adding: Like, Save-to-playlist, Comment-focus, Subscribe (native set omits these). Don't rebuild the many shortcuts YouTube already has.

### LinkedIn

> Most automation-hostile host here. All write-actions get conservative caps + immediate stop-on-restriction/CAPTCHA banner. Validate with DRY_RUN first.

#### 3.15 Bulk-withdraw sent invitations — ✅ FEASIBLE (MEDIUM)

- **Mechanism:** Pure DOM automation of LinkedIn's own UI (Feature-1 pattern) — no fetch, so no CSRF/Voyager needed. The v2 REST Invitations API requires OAuth partnership (unusable from a cookie session); DOM path is preferred and proven (halimbahae + several 2025/2026 scripts).
- **Hooks:** URL `https://www.linkedin.com/mynetwork/invitation-manage/sent/`. Query span/button whose `innerText.trim() === 'Withdraw'`, click; then click the inline confirm popover's "Withdraw" (also text-matched — it's a native inline popover, **not** a blocking `window.confirm`). Re-query after each removal; trigger scroll/"Load more" between batches (lazy-loaded — Feature-4 discipline). Pending sent invites cap ~500–700, fully enumerable.
- **Conventions:** `queue.js` with **its own conservative** randomized-delay + low daily cap; human-like pacing, never a tight loop; **stop immediately on any interstitial/CAPTCHA/restriction banner**. Labels in `config.js`.
- **Risk:** MEDIUM. Withdrawing your own stale invites is low-provocation, but rapid unthrottled clicking is exactly the "activity burst" LinkedIn flags ("LinkedIn jail"). The 3-week resend cooldown doesn't block withdrawing. Start conservative and observe.

#### 3.16 Bulk-remove 1st-degree connections — ⚠️ FRAGILE (MEDIUM)

- **Mechanism:** DOM automation (recommended) with a Voyager fallback — both cookie-authed, no signing/OAuth wall. FRAGILE, not impossible: the web client natively supports the exact action; risk is automation-detection + DOM/memberId brittleness.
- **Hooks:**
  - **DOM (recommended):** Connections list; row overflow "..." → "Remove connection" menu item (match by visible text) → confirm modal "Remove" button (match by text). MutationObserver on the confirm modal, mirroring IG Feature 1.
  - **API (fallback):** `DELETE https://www.linkedin.com/voyager/api/relationships/connections/{memberId}`, `credentials:'include'`, header `csrf-token` = the page-readable `JSESSIONID` cookie value (quotes stripped), `x-restli-protocol-version: 2.0.0`. **Friction:** the numeric `memberId` is hard to extract from the DOM — which is exactly why the DOM-click path is preferred.
- **Conventions:** `queue.js` with own conservative daily cap (like unfollow); **DRY_RUN mandatory first** — the DELETE is destructive with **no undo**. Stop-on-restriction.
- **Risk:** MEDIUM–HIGH (highest write-risk in this report). LinkedIn Help explicitly prohibits automation extensions and actively restricts accounts; commercial tools remove one-by-one specifically to dodge detection. Personal, low-volume, throttled use only.

#### 3.17 Hide promoted content — ⚠️ FRAGILE (MEDIUM/HIGH)

- **Mechanism:** Pure read-only DOM filter — zero ban risk (nothing sent). FRAGILE purely because LinkedIn has **no stable semantic hook**: feed items lack `role="article"`, and the "Promoted" label is an active anti-adblock target (split across spans, zero-width chars injected, localized) that breaks naive text matching.
- **Hooks:** match the "Promoted" label via **robust text-node inspection** (handle split/hidden-character text), fall back to feed-item container traversal. **Do NOT use** `[data-control-name='actor']` (undocumented internal attr LinkedIn rotates) or auto-hashed utility classes.
- **Conventions:** marker text/variants in `config.js`; expect frequent selector maintenance. Note: BrowserGate (Feb 2026) passively scans for `chrome-extension://` URLs — no ToS violation from DOM filtering itself, but keep injected markup `bwi-` namespaced and minimal.
- **Risk:** LOW account risk / HIGH maintenance. Build only if you'll commit to touch-ups.

## 5. Recommended build order

Ordered by: (feasibility confidence) × (low ban-risk) × (user value) × (reuse of existing architecture). Read-only DOM wins and already-built verifications come first; high-risk LinkedIn writes last.

1. **IG see-who-unfollowed — verify & harden** (§2.1). Already built, read-only, HIGH confidence, no ban risk. Fix the partial-fetch guard + honest labeling. Fastest real win.
2. **X: hide promoted / algorithmic content** (§3.5). Read-only DOM, zero ban risk, HIGH confidence, high daily value. New host bootstrapping is cheap.
3. **Reddit: hide promoted posts** (§3.10). Read-only DOM, zero risk, HIGH confidence. Mandated "Promoted" label = stable hook.
4. **X: chronological feed enforcer** (§3.3). Pure DOM, minimal risk, HIGH confidence, high daily value. (Remember the second "Recent" sort click.)
5. **YouTube: bulk-remove Watch Later** (§3.12). DOM-click through `queue.js`, HIGH confidence, big user value, textbook reuse of the queue. Async-deletion delay is the only gotcha.
6. **YouTube: bulk-unlike Liked videos** (§3.13). Same mechanism as #5 — near-free once #5 ships.
7. **Reddit: bulk-unsave** (§3.9). DOM primary + cookie/modhash fallback, HIGH confidence; shadow-DOM piercing is the extra work. Direct parallel to IG Feature 4.
8. **X: bulk-unfollow non-followers** (§3.2). HIGH confidence, source-proven; but a mutating action with real caps → sequence after the safe DOM features. Own daily key.
9. **X: keyboard shortcuts parity** (§3.4) & **YouTube: keyboard shortcuts** (§3.14). LOW risk, HIGH confidence; low urgency (native sets already cover a lot). Bundle them.
10. **TikTok: bulk-remove favorites** (§3.7). DOM automation, MEDIUM confidence; new MAIN-world host + selector re-derivation is the cost.
11. **TikTok: bulk-unlike** (§3.6). MEDIUM confidence, private-API kill-switch risk; run the DevTools X-Bogus check first.
12. **X: bulk-unlike** (§3.1). MEDIUM confidence, DOM-click primary; mass irreversible → confirm gate.
13. **IG enhanced story composer — rebuild scoped to text/drawing** (§2.2). MEDIUM, cut stickers, verify upload live first. Lower priority — mostly a de-risking/cleanup of existing code.
14. **LinkedIn: bulk-withdraw sent invitations** (§3.15). MEDIUM, hostile host but low-provocation action. Conservative caps.
15. **LinkedIn: hide promoted content** (§3.17). Zero ban risk but HIGH maintenance — build only with a maintenance commitment.
16. **LinkedIn: bulk-remove connections** (§3.16). Last. Highest write-risk, destructive, no undo. DRY_RUN + tiny caps + stop-on-restriction, or defer entirely.

**Cleanup tasks (do alongside):** rip out the `feature9.js` story-repost live path and the `configureToStoryApp()` app-tier call (§2.3, active account-safety hazard); retire the `mainworld.js` carousel interception (§2.4).
